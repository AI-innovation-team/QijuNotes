# 部署与恢复执行指南

## 1 执行依据与环境边界

产品与技术基线为[包根SPEC_v1.1.md](../SPEC_v1.1.md)，能力验证从[tasks/P0_CAPABILITIES.md](../tasks/P0_CAPABILITIES.md)开始。按基线实施默认每日唤醒、历史空缺补填和每项活动持续深聊；不得恢复旧版自动降频、活跃度判定或因用户沉默而暂停的逻辑。

先判断当前执行环境是否就是用户指定的Linux主机。本任务包编制时没有目标主机访问，也没有已验证的安装版本。若仍无目标访问，完成固定版本的本地开发、隔离验证、部署配置和恢复脚本，将真实环境检查标为PENDING_TARGET_HOST；不要把当前容器检测结果写成目标主机事实。

具备访问后，先只读盘点发行版、架构、运行身份、服务管理方式、Node与DSH来源、已有实例、监听端口、数据目录、模型路由、可用磁盘及备份位置。检查凭据是否可用，不打印密钥或完整环境变量。确认现有实例归属，保存必要配置副本，使用独立测试目录；不要覆盖既有部署或删除历史数据。

## 2 固定版本并执行七项探针

从所选版本的官方manifest、CLI帮助、源码及必要插件作者资料确定安装方式和调用接口。记录版本或提交、依赖锁定信息、插件清单及配置位置；不以持续变化的latest或未经核实的命令作为生产基线。先搭一个可运行的最小个人活动插件，再验证下表。可使用固定模型响应降低成本，但必须标明模拟范围，并补做一次实际模型的小规模验证。

| 探针 | 必须执行的操作与通过证据 |
| --- | --- |
| 环境与版本 | 保存脱敏盘点、固定版本清单、测试与生产路径边界；证明所选运行环境能够启动，并能读取最终生效配置。 |
| timed与持续会话 | 创建独立活动，令原生问题进入pending；结束轮次并重启隔离宿主，再回答原问题；基础摘要后继续追问。核对活动、Session和问题定位未串接，pending未推进步骤。 |
| 持久入站 | 令模型凭据无效或供应商不可用；回复获得持久回执后立即终止测试宿主，再恢复。同一提交ID重试只处理一次，正文可找回；核对原生inbox或项目入站队列与DSH事件的交接。 |
| 调度与归属 | 用注入时钟测试三类日程、重复触发、跨日和重启，不修改系统时间。无人回复仍每天触发；明确暂停才停。补填历史日期时复用已有活动或按原日期补建，不影响当天唤醒。 |
| 看板与验收 | 执行一个仅生成测试文件的明确委托，保留实际成果及执行记录；验证Agent无法自行验收。用测试用户交互路径验收指定版本，返修后新版本重新待验收。 |
| 服务与手机 | 验证隔离服务重启、关闭浏览器或SSH后的运行及非交互模型调用；实际手机访问和通知另留真机证据，模拟请求不能替代设备测试。 |
| 备份与恢复 | 备份隔离实例，随后新增回复、删除测试内容并记录模拟外部动作；恢复旧快照，验证新账本核对及缺账本时隔离、不重放的行为。 |

原生timed应在固定版本实际启用的preset中配置，核查最终生效结果，不能只在prompt中要求等待。日常交互Session只由一个活跃Web宿主写入；共享DSH_HOME不能证明多进程并发安全。重复启动须由验证过的归属或锁机制阻止竞争写入。

P0必须留下“触发—唯一活动—页面提问—轮次结束—晚答保存—原会话继续—摘要更新”的运行证据。发现原生缺口后，记录具体适配方案并实现最小补齐，不停在资料综述或插件候选清单。DSH接口名称必须来自固定版本；项目逻辑接口不得冒充原生API。

## 3 安装与常驻运行

核心版本、会话、持久入站及唯一调度探针形成可实施主路径后，立即按已验证接口生成可重复安装与启动脚本、服务配置和脱敏配置样例；服务自启、真实手机及完整恢复探针按部署依赖继续补验，不作为生成部署材料或推进其他开发的前置条件。未完成验证保持对应待验证状态。主路径为一个常驻DSH Web宿主及个人活动插件；A1–A3只有一个调度入口，看板仅调度明确委托。若采用routines替代触发适配，先撤销原注册，禁止两套调度同时生效。

配置明确服务身份、绝对工作目录、数据位置、必要环境、日志和启动依赖。服务不得依赖交互shell或持续SSH连接。采用用户级服务时，必须验证退出登录后的运行条件，不能仅凭服务已启动宣称开机自启完成。整机重启只在已授权维护窗口执行；此前完成隔离服务重启验证，保留冷启动证据待补。

## 4 手机入口与通知

根据实际手机系统和网络条件选择受认证的访问路径；不从电脑系统推断手机类型。验证电脑发起、手机回复、电脑可见，以及锁屏重开、网络切换、通知直达指定活动。主页面可访问与锁屏主动通知分别验收。

记录通道真实支持的发送、送达和已读状态。文件生成、推送接口接受不能冒充手机已读。通知只包含事项类型及入口，重试沿用效果标识；结果未知先核对，避免重复发送。缺设备或通道凭据时继续其他工作，标记PENDING_REAL_DEVICE或具体配置缺项。

## 5 预算与运行检查

采用基线默认额度：后台每日60000、每月1000000个输入与输出token，单次最多8192个生成token；按实际模型口径纳入推理消耗。后台并发默认2，重试最多2次。全部后台请求及各层重试统一准入，预留和结算持久化、原子更新；未知用量保留预留，重启不能清零。主动请求与明确委托分开记账。

验证双并发不超占、额度不足暂停生成但仍保存回复、模型恢复后续接而不要求重答。检查页面能说明最近成功、失败原因、待处理摘要、预算和备份状态。已保存必须对应持久回执，前端乐观显示不能作为证据。

## 6 一致性备份、迁移与回退

在协调检查点或短时停止写入后备份：会话与附件、未交接入站记录、业务数据库、人工修订、画像、看板账本和附件、成长资料、preset、skill、配置及版本清单。数据库采用其支持的一致性备份方法；看板JSON不包含的图片目录必须单独覆盖。异机副本加密，恢复口令不能只放在唯一备份中。

修订／删除账本和已发生外部动作记录独立持续保存，记录最新保护时间。恢复旧快照先隔离，停用全部调度、自动续跑、待执行效果和通知；核对较新账本与通道回执后才放行。缺少覆盖时间段的记录时标为状态未知，不直接重放，也不把可能失效的历史重新注入模型。

在干净目录或备用实例恢复，核对原文、活动、任务、摘要、画像、成长关系及附件，重建索引；凭据重新配置，不依赖旧绝对路径。升级先在副本验证迁移、晚答及返修，再准备应用与数据成对回退。没有异机目标时只报告同机恢复结果，不能宣称机器故障保护已具备。

## 7 进度、证据与继续执行

持续更新开发仓库根目录的progress/PROGRESS.md，中断或阶段切换时更新progress/HANDOFF.md。每项探针和部署检查在开发仓库的evidence/保存版本、环境、输入、预期、实际结果、必要稳定ID及证据位置；区分模拟、实际模型、目标主机和真机。这些目录在实施时生成，不位于本包operations目录内。

只对证据支持的范围标PASS。可补齐的技术缺口直接落实适配并继续后续任务，不例行询问是否继续；外部条件不足仅阻塞相应验收。最后交付可重复启动、诊断、备份、恢复和回退入口，集中报告仍需用户提供的具体条件，不以安装成功代替完整产品验收。
