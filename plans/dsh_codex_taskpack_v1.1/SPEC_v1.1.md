# DSH 个人成长与起居注系统技术开发文档

**版本：开发基线 1.1（已吸收2026年10月22日确认与修订）**  
**日期：2026年10月22日**  
**运行环境：用户自有 Linux 主机；电脑与手机访问同一服务**  
**默认业务时区：Asia/Shanghai**

本系统围绕“博士学位、科研创业、文化事业”三条主线，提供每日一学、每日反思、睡眠打卡、完整起居注、定向摘要、任务执行与成长复盘。目标是减少日常记录和协作负担，让已经发生的交流和工作持续形成可查证、可纠正、可迁移的个人资料。

本文是Codex开发任务包的产品与技术基线。用户已确认其余规格，并明确修订：默认每日唤醒，只有用户明确表态才改变频率或暂停；提供前几日空缺的补填入口；每项定时活动始终支持持续深入的聊天。1.0中的自动降频阶梯、低参与阈值与相关验收要求已经撤销，不得继续实现。其他工程默认值可以在设置中调整。本次确认是开发范围确认，不代表目标主机已部署或验收通过。

## 1 产品原则与范围

### 1.1 已确认的四项原则

1. **独立活动允许随时续答。** 每次活动拥有独立身份和会话。用户晚回复、换设备、服务重启或活动进入历史后，仍可继续原活动。
2. **每日唤醒，交互低负担，调整由用户明确决定。** 系统尊重简短回答、单次跳过和阶段投入差异；不根据沉默、短答、已读未答或活跃度自动降频。用户可以明确调整时间、频率和暂停范围。
3. **记录和画像能够纠错。** 用户能够查原话、更正摘要、修订背景与偏好，并使更正作用于后续服务。
4. **明确委托直接执行，成果由用户本人验收。** 已授权且必要信息充分的委托直接进入执行或排期；Agent 提交成果和证据，用户决定接受、返修或取消。

日常打卡、后台保存及摘要更新不额外要求逐条人工验收。用户明确委托的范围、既定权限和平台约束共同限定执行边界；超时不构成对额外操作的授权。

### 1.2 必须覆盖的功能范围

| 模块 | 交付要求 |
| --- | --- |
| 每日一学 A1 | 每日21:00触发准备；典籍一段、史事一则、概念一个；可深入讨论和回看 |
| 每日反思 A2 | 每日21:30触发准备；默认按博士学位、科研创业、文化事业逐项交流；支持自然补充和跳过 |
| 每日打卡 A3 | 默认每天08:30，以睡眠为切入点；接受简短回复与深入讨论；日程仅按用户明确指令调整 |
| 历史补填 | 页面与自然语言均可选择前几日或任意历史日期；已有活动续答，缺失活动按原日期补建，不影响当天唤醒 |
| 起居注 H1–H3 | 覆盖约定范围内的完整日常对话，按日及周索引浏览，保留可读原文和成果引用 |
| 定向摘要 | 仅针对A2/A3的用户实际回答形成结构化摘要，允许部分记录、补答和更正 |
| 任务看板 G2 | 明确委托建卡、排期、执行、交付、返修和用户验收；浏览器关闭时仍能执行 |
| 成长线 G1 | 画像、能力证据、阶段计划、今日行动、成果证据与周期复盘持续关联 |
| 多端与数据 | 电脑直接使用DSH Web；手机为主要移动入口；本地保存、标准导出、迁移与恢复 |
| 初始材料导入 | Kimi、Codex及ChatGPT历史；分别处理工作指令、个人记忆与会话材料 |
| 长期运行 | 开机自启、有界执行、可见故障与预算、加密备份、容量治理和可恢复升级 |

首版面向单用户。它可以通过任务委托调用已有科研工具，但不在本轮重建科研图画布、论文编辑器或完整科研工作台。

### 1.3 范围边界

- 全量起居注的保证范围是本实例内的日常交流与主动导入的历史。外部平台未来新增的对话，不因一次导入而自动持续同步。
- 原文记录不由模型判断“是否重要”后再取舍。长工具输出可以折叠显示并保留定位，不能因摘要遗漏而丢失。
- 手机和电脑共享已提交消息与活动进度；跨设备未提交草稿同步列为增强项。同一浏览器且本地存储可用时，页面刷新及短时切后台后应恢复未提交草稿，明确标识未发送；保存失败显示提示。用户清除站点数据或浏览器删除本地存储不在草稿恢复保证内。
- QQ/微信作为辅助通知和有限文本保底候选，不承担唯一入口、成果审批或长文审阅；具体接入仅在通道可用且授权明确后实施。
- 成长线不能替代三个日常任务；复杂能力评价可以渐进完善，但完整范围交付必须走通真实成长闭环。
- 不以插件安装成功或页面存在代替产品完成。

## 2 日常使用与统一入口

### 2.1 今日入口

DSH内提供一个稳定的“今日”入口，聚合以下内容，活动继续保留各自独立会话：

- 今天的学习、反思和打卡。
- 当前等待用户回答的问题。
- 正在执行、需要补充信息、等待验收的委托任务。
- 历史日期入口、全文搜索、学习收藏及成长回顾。
- 用户明确设置的日程或暂停状态、下一次时间及需要处理的运行异常。
- “补填前几日”入口：近7天快速浏览并可选择其他历史日期。

用户从通知链接进入时，直接打开该活动及当前问题；普通启动时恢复合理的最近位置。“恢复上次会话”不能覆盖通知的明确目标。

今日入口默认突出当天活动。历史未答项进入历史中的“可继续”列表，不持续积累红点；用户明确置顶的事项例外。跨日移动展示位置不删除活动、不改变原文，也不关闭续答入口。

### 2.2 一天的基本流程

| 情境 | 规定行为 |
| --- | --- |
| 08:30打卡触发 | 问题就绪后用户可以一句话回答，运动和情绪可选；持久保存后展示简短确认及修改入口 |
| 白天聊天和派活 | 主会话可正常使用，早上的待答事项不占住执行槽 |
| 21:00学习触发 | 内容就绪后显示三项短版，允许展开、追问、收藏或结束本次阅读 |
| 21:30反思触发 | 独立创建反思并准备问题；正在学习讨论时不切页面、不抢焦点、不覆盖输入 |
| 晚回复和补录 | 继续原日期的活动，同时保留实际回复时间 |
| 用户明确调整频率或暂停期间 | 手动聊天、主动打卡、补录历史和查看资料仍然可用 |

到点代表触发准备并在完成后呈现。界面区分“正在准备”和“已就绪”，记录实际触发时间与就绪时间，不把计划时间当成要求用户到场的截止时间。学习材料可以提前准备，但不提前通知、不改变业务日期；失败时显示原因和重试状态。验收分别检查准时触发、生成延迟和结果状态。

### 2.3 通用控制

自然语言与页面控件应覆盖：继续、跳过本次、结束本次、稍后提醒、暂停到指定日期、调整时间或频率、恢复、补记某天、纠正记录、打开原文、明确建任务、验收通过及要求返修。

对“明早”等表达，使用已设置的默认上午时间并回显完整日期、时间和时区；未配置且无法从上下文确定时，只补问必要的一项。不会因参数可以再优化，就对一个已经明确的委托重复请求许可。

### 2.4 前几日空缺与补填

今日入口提供“补填前几日”，默认展示近7天并可切换到任意历史日期，7天只是初始视图范围。支持“补记昨天的睡眠”“把前天的反思继续聊完”等自然语言操作，回显明确日期、活动类型和时区；指向清楚时直接进入。

缺口视图区分：已有活动尚未答、已有部分记录可补充、已有基础记录可继续聊、计划日因故未创建，以及用户已跳过、暂停或非计划日。这些状态分别呈现；已跳过、暂停、非计划日和选填字段缺失不算“欠账”。A1已生成材料但尚无讨论时显示“可补学／继续讨论”，不把没有聊天认定为没有阅读或没有掌握。

1. 已存在对应活动时，打开同一活动并恢复已有进度，不再创建副本。
2. 所选历史日期尚无对应类型活动时，仅按该日期和类型补建，并标记“补记／补学”；不自动生成多日积压。
3. 支持一次选择多个日期逐项补填，也接受一次消息覆盖多日；日期指向明确时分别归属，含糊时只澄清必要日期，不把同一段原话复制成多份独立事实。
4. 活动和定向摘要归属原业务日期；原文保留实际补记时间，并在当前日期起居注与原活动之间建立引用。不能将今天补记伪装成过去当日提交。
5. 历史补填不补发原日期的首次通知，不消耗或取消今日活动；今日活动只依据今天自己的状态决定是否已完成。
6. 补填后更新原活动摘要、日期索引、相应周回顾及成长证据，保留用户更正。历史A1临时生成内容时标注实际生成时间，不冒充当时已存在的材料。
7. 已跳过或用户暂停期间的日期也可主动补记；未经用户选择不自动补建。已删除内容按6.5处理，补填不得绕过删除账本复活旧资料。

部分填完即可离开；系统不要求一次清空缺口，也不增加补填催促。首次启用前的历史可主动录入，但不自动列为漏填。

## 3 三类日常活动

### 3.1 A1 每日一学

**触发时间：每天21:00，Asia/Shanghai。**

内容同时包括：

1. 四书五经、法家、兵法等典籍中的一段。
2. 二十四史、近代史、党史等材料中的一则史事。
3. 一个现代政治、经济、金融或货币相关概念。

讲解围绕修身立德、认识世界、改造世界，保留材料本身的语境与适用边界。每项包含出处、必要背景、主要解释及一个可讨论的现实联系。原文、史实、解释和应用建议要可区分；争议材料说明争议，查不到可靠出处时换用可核查材料，不编造出处。

默认三项采用短版，完整内容可展开；总阅读量以约五分钟为初始体验目标。用户主动追问可以深入，不受短版篇幅限制。三项可以形成阶段主题，但不强行拼成同一结论。

系统保存主题、来源、首次学习日期、收藏、追问和复习记录。近期重复材料须标明“复习”及原日期。阅读、收藏、用户自评和能力判断分别记录，不能从“看过”直接推断“掌握”。

内容就绪后询问用户希望深入哪一项，并允许“今天到这里”。用户没有回答时，活动保持可继续；默认不追加自动催促。

### 3.2 A2 每日反思

**触发时间：每天21:30，Asia/Shanghai。**

默认依次讨论博士学位、科研创业、文化事业，每个维度先提出一个主要问题。问题围绕实际进展、认识、约束和下一步，不要求每天三条主线都有成果。用户在当前维度继续展开时，先承接讨论，不因已有一句回答就强行切换下一维度。

业务规则：

- 当前维度已得到基本回应且用户没有继续展开意图时，自然进入下一个尚未处理的维度；明确要求继续深入时留在原维度。
- 一次回答覆盖多个维度时，保存对应内容并跳过已经回答的提问。
- “无进展”“本周未投入”“今天不想谈这一项”均为有效表达。
- 用户可以只谈某一主线、中途暂停、跳过或补充。
- 必要澄清默认每个维度最多一次；用户主动展开不受此限制。
- 待答、超时或进程退出都不自动视作已回答。
- 白天任务信息可辅助提问，但只有用户在该活动中的实际陈述进入A2定向摘要；外部证据以来源链接另列。

每次有效回复先保存原文及进度，随后更新部分摘要。摘要包括实际进展、主要认识、问题与约束、已明确的决定、下一步和需要Agent协助的事项；未提供的字段保持未知或未回答。

整体状态总结是可修订的概括，不能擅自推断人格、心理诊断、思想水平或长期能力。活动结束后仍可补充并更新同一活动的摘要。

### 3.3 A3 每日打卡

**初始日程：每天08:30，Asia/Shanghai。**

默认只问一个开放问题：昨晚到今早睡得怎么样？睡觉时间、起床时间或主观质量，任选一项说说即可。睡眠质量允许文字或1–5分，数字尺度须在界面清楚说明。

“00:30睡、08:10起、3分”“睡得一般”都属于有效回答。信息足够就停止例行盘问；必要澄清默认最多一次，但输入框和对话始终可继续。用户愿意讨论睡眠、运动、情绪或行动安排时正常深入，不能以“打卡已完成”拒绝继续。运动和情绪选填，实际活动与未来计划分别保存，缺失值不填成零或负面状态。

不重复发送固定说教段落。提交后简短确认，展示系统提取到的记录并允许直接修改。次日补记应明确所指睡眠区间；跨午夜的睡眠记录默认归入起床日期，用户可更正。

### 3.4 每日唤醒与用户明确调整

A1、A2、A3默认每天按约定时间触发。昨天没有回答、连续多日未读、只说“收到”、简短回答、已读未答或单次跳过，均不改变后续日程；不设置自动降频阶梯，也不依据参与统计让系统自行减少唤醒。

“今天先不聊”只作用于本次活动。“改成每周二、四”“暂停到下周一”“恢复每天”等明确指令直接改变指定例程，并回显生效时间、下一次触发及恢复规则。仅调整A3不连带修改A1/A2；指向或日期确实不明时只澄清必要部分。每次日程变更保留对应用户指令或操作来源，后台模型无权凭自己的判断改日程。

有限期暂停按已明确的日期到期恢复原日程；这是执行原指令，不是系统自行改变频率。暂停结束后从下一个未来时点继续，不自动补建暂停期间活动。用户仍可主动补记、聊天和查看资料。

“每日唤醒”指每个计划日创建或复用当天活动，并按4.4执行一次首次呈现或通知；不要求用户按时到场，也不对同一天反复追催。用户提前完成当天基础活动后，到点不重复提醒；补填历史不算今天已经完成。服务或通道故障、预算不足须明确显示，不得被写成用户同意降频或暂停。

### 3.5 所有例程都是可持续的聊天

A1、A2、A3的短内容和默认问题用于降低开始交流的成本，不构成固定问卷或聊天轮数上限。三项活动均支持自由输入、持续追问、查证、展开、补充与更正，保留当前讨论上下文；用户明确委托时可从讨论形成关联任务。

基础记录完成、摘要已生成和用户结束本轮聊天分别记录。摘要生成不能自动关闭输入框；“今天到这里”可以收束当前交流，后来仍能继续原活动。每次新回复更新同一活动的有效摘要与相关证据，A1讨论仍不混入A2/A3定向摘要。

默认一次澄清只约束没有额外请求时的例行盘问。用户继续展开后，Agent正常接续、追问和研究；不能机械套用一次上限。实际模型调用仍受明确预算和单次执行超时约束，等待用户不占执行槽，也不因等待超时强行推进或关闭活动。

## 4 活动状态 调度和通知

### 4.1 三种完成不能混用

| 层次 | 典型状态 | 判定依据 |
| --- | --- | --- |
| 一次计算 | 排队、运行、成功、失败、取消 | 本次模型或工具操作的实际结果 |
| 日常活动 | 准备中、待回复、部分完成、基础记录完成、用户已结束、已跳过 | 用户交流进度及明确操作；基础记录完成不关闭聊天 |
| 委托任务 | 待执行、执行中、待补充、待用户验收、已验收、返修、取消 | 委托执行和用户验收行为 |

另行记录通知的待发送、接口已接受、可核实送达、可核实已读、失败、未知。通道无法证明的状态不得伪造。内容生成成功、通知成功和用户回复互不替代。

活动进入历史是展示状态；不构成禁止继续的终态。只要原记录未被明确删除或按用户选择移除，已结束、已跳过和已归档活动都允许补充。补充保留原活动身份和原日期。

### 4.2 时间归属与唯一性

至少分别保存业务日期、计划时刻、实际创建时刻、消息接收时刻、材料原始日期及导入时刻。持久时间戳采用明确时区约定，展示按业务时区转换。

A1–A3以“用户、例程类型、业务日期”形成逻辑唯一键。修改prompt、服务重启或手动重试不产生当天第二个活动。用户明确重新生成内容时，增加同一活动的内容版本；不丢弃已有讨论。

改变日程只作用于后续计划，并回显下一次时间。用户主动提前完成当天打卡后，到点不得再次创建和提醒。历史等待用户的活动不能占住模型并发槽，也不能被重叠运行保护误判为今天仍在执行。

### 4.3 漏跑与故障恢复

默认恢复策略：

- 服务恢复时只补建当日按实际日程本应触发、已经到点但尚未创建的活动；用户明确设置的非计划日不算缺失。
- 同一活动最多补建一次，默认静默呈现并标注实际就绪时间，不补发已错过的首次通知。已有活动只恢复未完成步骤，不重新建活动或重新消耗首次通知机会。
- 不自动补建过去多天的学习、反思和打卡；记录遗漏原因，并由2.4的历史入口供用户按需补填。禁止批量自动重放不限制用户主动补建。
- 暂停期间本来不应触发的活动不记作失败或缺席。
- 明确委托的一次性任务单独设置“截止前补跑／错过则提示”；截止或对外影响不明确时，不能一概套用日常问候规则。
- 仅重试失败步骤：通知失败重试通知；摘要失败重试摘要；用户回答已保存时不得要求重答。

正常到点创建后发生的通知投递失败，仍按有界重试和免打扰规则处理，与停机后补建活动分开。此处是进程正常重启的恢复策略；从旧备份恢复须先遵循9.4的隔离核对规则。

业务处理采用可重试且幂等的方式。外部通道若不支持幂等键，发送结果不明时标记“结果未知”，先核对回执，不盲目重发。不得笼统承诺所有外部操作严格只发生一次。

### 4.4 通知默认值

- 每项活动一次首次通知，零次自动追催。
- “稍后提醒”增加用户指定的一次提醒；新选择替换尚未发送的同类提醒。
- 默认免打扰为23:00–08:00，可修改。
- 最近五分钟有前台交互，且当前至少一个已连接、可见的页面确认呈现该活动的就绪提示时，才抑制本次外部首次通知；仅有历史活跃时间不构成抑制条件。页面已断开或提示未确认呈现时，仍按一次首次通知处理。就绪提示不抢占输入、不切换会话，已确认呈现后不另补发同一次通知。
- 一个活动选择一个主要通知通道；备用通道仅在明确投递失败或既定切换规则下使用。
- 通知正文默认只含事项类型和入口，不展示睡眠、情绪或反思正文。
- 外部通知通道尚未接入时，状态必须说明“仅页面可见”，不能将文件落盘当作已通知手机。

主入口必须支持手机访问。锁屏主动提醒是单独的交付能力，须通过选定实际通道验收；通道未具备时保留待验证状态。

## 5 委托任务与用户验收

### 5.1 从表达形成任务

“记个想法”进入想法记录；“也许以后做”进入可选候选事项；“请明天完成这份整理”属于明确委托，可直接创建任务并排期。不得把每句话都转换为待办。

任务至少包含：目标、负责人（用户／Agent／共同）、必要输入、交付物、执行时间、验收条件、来源活动或消息、当前状态、执行记录及成果位置。条件充分时，Agent可以把常规验收条件一并整理成可见说明，无需增加一轮例行许可。

上下文中已授权的可执行步骤继续进行。必要输入缺失、执行边界不明或需要超出既有授权时，只提出具体缺项，并保存可恢复的等待状态。

### 5.2 执行与交付

支持立即执行、一次性定时和周期任务。调度发生在Linux服务端，浏览器关闭不影响执行。每次执行拥有独立记录；默认独立执行会话，任务卡持续关联全部执行和返修。

成果提交包括：完成了什么、成果入口、如何验证、剩余限制。执行成功进入待用户验收。Agent负责执行中的检查和测试，最终验收以用户明确表示为依据；不能把Agent自检通过当成用户已接受成果。

用户可以通过验收控件，或在能够明确定位成果版本的对话中说“这版验收通过”等完成验收。系统记录用户原始输入、执行记录及成果版本；沉默、Agent自身判断或意思不明确的附和不构成验收。目标版本不清楚时只澄清版本，不重复询问已经表达清楚的验收意愿。

验收绑定具体成果版本。返修产生的新版本重新进入待用户验收，旧版本记录保留，不自动复制通过状态。返修追加在原任务和原成果关系中，不能自动拆成与来源无关的新卡。

日常活动不因看板而每天多出三张待人工验收卡。用户的运动、阅读等本人行动可以记录和跟踪，但Agent不得把提醒发出写成行动已经完成。

周期委托的本轮验收与下轮计划分别保存。周期授权仍有效时，下轮可以继续；同一任务的实际执行默认不重叠，待验收本身不占计算槽。用户取消周期授权后，所有未来触发停止，已提交成果保留。

### 5.3 并行与权限

日常活动待答不阻塞主会话派活。默认后台实际生成并发上限为2，前台问答有优先级；耗时任务可以排队并显示原因。任务执行是否另设并发由目标主机资源确定。

权限审批与普通提问采用不同状态。审批请求在有界窗口内处理；无答复时停止该项需授权的动作并记录原因，不擅自扩大权限，也不将整张任务写成已完成。用户后续处理后可以继续相应步骤。

## 6 原始记录 摘要和画像

### 6.1 数据职责

| 对象 | 权威内容 | 派生形式 |
| --- | --- | --- |
| DSH会话 | 原始消息、工具与问题事件、附件定位 | 完整可读对话、时间线、搜索索引 |
| 个人活动 | 日期、步骤、回答引用、跳过状态、日程与会话关联 | 今日入口、活动历史 |
| 定向摘要 | 从指定活动回复形成的当前摘要及用户更正 | 日／周摘要、成长证据引用 |
| 用户画像 | 已确认背景偏好、作用域、有效期、来源及推测状态 | 按当前任务选取的上下文 |
| 委托任务 | 看板账本中的任务、执行、交付及用户验收 | 任务列表、成果索引 |
| 成长计划 | 目标、能力证据、行动和复盘版本 | 周回顾、90天计划视图 |

每类对象只有一个权威写入路径。业务表引用原始消息定位，不维护两套互不一致的问答正文。Markdown负责标准可读导出；首版通过界面或明确自然语言修改权威对象后重新导出，不承诺任意Markdown文件编辑与数据库自动双向合并。

### 6.2 完整起居注

覆盖白天派活、临时提问、灵感、闲聊以及A1–A3交流。默认保留用户可见对话正文、时间、角色、来源会话、附件和成果引用。工具执行细节可分层折叠，保留原始定位；模型内部不可获得的隐含状态不作为交付内容。

提供按日完整记录、按周索引及关键词全文搜索。长会话按消息日期进入相关日索引；同一消息以稳定ID避免重复。日索引链接到完整原文，不能只提供模型摘要。删除摘要后，原文仍能独立阅读。

归档以已持久化的新事件为依据持续增量处理，并做周期核对；不能仅在会话结束、达到某个文件增量大小或模型主动调用归档工具时才保存。跨日、未结束、迟到回复和失败运行中的已提交消息都在覆盖范围内。

### 6.3 A2/A3定向摘要

来源通过活动类型和消息引用精确选择，不能仅靠模型从全天对话中猜测筛选。

- A2：进展、认识、约束、明确决定、下一步和协助需求。
- A3：实际提供的睡眠时间、主观质量、活动及感受；实际发生与计划分开。
- 用户事实、主观感受、用户决定和Agent建议分别呈现。
- 缺失字段明确为空或未知，不把未答解释为零、否或负面状态。
- 每次回复、补充或更正均更新同一活动摘要，保留覆盖范围和版本。
- 原文先保存，摘要随后生成；失败只影响摘要状态。
- 生成结果提交前核对输入版本，过时结果不能覆盖更新的回复或用户更正。
- 人工更正作为持续有效的修订输入保存；后续即使使用最新回复重新生成摘要，也不得重新提取旧原文而撤销更正。新陈述与既有更正冲突时，保留出处并按明确修订关系处理，无法确定时保留冲突而不静默选择旧值。
- A1学习讨论保留在起居注与学习历史，不混入A2/A3定向摘要。

### 6.4 画像导入与更新

F1为Kimi材料；F2为Codex会话、AGENTS.md及可用memory材料；F3为ChatGPT会话和用户提供的Memory材料。每类导入均展示来源、数量、时间范围、重复项与失败项，支持预览及重复导入去重。

保留导入批次、原始来源文件或可核对指纹，以及附件缺失清单。支持按批次移除该批新增记录及派生项，不误删此前已存在的相同内容。导入的AGENTS.md先作为有作用域的来源资料处理，不因出现指令文字就自动执行或覆盖当前系统规则。

ChatGPT导出的会话与手动Memory材料分别处理；Codex工作规则与个人记忆分别处理。文件路径、格式和可用字段以目标环境实测为准，不将某个历史目录模式写成永久保证。

画像条目最少保留：内容、类别、来源定位、原始日期、导入时间、作用域、有效期、确认状态、替代或撤销关系。类别包括背景偏好、项目规则、阶段目标和待讨论推测。

用户近期明确更正优先于旧材料；项目内要求不自动变成全局偏好。Agent可以提出画像更新建议，但不能把推测无标记升级为稳定事实。明确说“记住我以后……”可直接更新相应偏好并回显；普通反思不触发每条都要确认的画像审查。

### 6.5 纠错 删除和重建

支持修改摘要、纠正记录、停用某项长期记忆、调整作用域和删除指定内容。修改保留来源及修订关系；后续上下文、检索和成长视图以当前有效版本为准。

删除操作说明作用范围：当前原始记录、派生摘要、索引、画像引用、导出及备份分别如何处理。通过支持的接口处理DSH原始存储；某类底层删除尚不支持时，不宣称已经彻底删除。

删除生成不含原文的最小清单，记录对象标识、来源指纹、删除时间及必要作用域；更正记录保留有效修订关系。最新修订与删除账本独立于历史恢复点保持更新，并纳入加密异机保护。重建或重复导入先应用该账本，避免旧内容重新成为有效记忆。

旧快照自身无法提供快照之后发生的删除或更正。从旧备份恢复时，须先合并最新可得账本，再开放相关检索、画像和模型上下文；无法取得覆盖所需时间范围的账本时，受影响内容保持隔离及待核对，不能宣称删除一致性已经通过。历史加密备份中的副本按明确保留期退出；用户可选择提前销毁对应备份，操作受既有授权范围约束。

“不要作为长期偏好”只停用画像使用，不能被误解为已删除所有原话；“删除这段原话”则必须处理其派生引用。

## 7 成长线

### 7.1 持续闭环

成长线持续连接：已确认背景与目标、能力证据、阶段计划、当日行动、实际成果、用户评价和下一次调整。三个日常活动提供输入，委托任务提供执行与成果，二者都保留原有身份。

三个主线可以采用不同指标：

| 主线 | 优先呈现 |
| --- | --- |
| 博士学位 | 培养节点、研究问题、实验与分析成果、论文及近期约束 |
| 科研创业 | 产品假设、用户反馈、验证结果、交付和资源投入 |
| 文化事业 | 阅读、写作、作品、活动、认识变化及阶段关注 |

不强制三条主线平均分配时间。阶段性低投入可以是用户明确选择。没有记录、本周未开展、受到阻碍和能力下降分别表达。

### 7.2 能力模型与阶段计划

能力模型以能力项、当前证据、待验证判断和下一次验证机会组成，不从聊天数量自动生成总分或人格定性。每项判断能打开证据，用户可以更正或停用。

90天计划为可调整的阶段范围，保存目标、约束、近期行动、预期产物、复盘日期和当前版本。提出新计划不自动增加一批已授权执行任务；用户确认阶段安排或明确委托后，再按其授权形成任务。

周回顾作为持续更新的视图，展示事实、证据、用户评价、未解决问题和拟调整事项。以Asia/Shanghai自然周归属，区分“本周截至目前”和“上一完整周”。默认不增加独立的强制问答或第四条推送，用户可主动打开；自动整理复用日常更新和维护流程。

三条主线均须分别验证目标、能力证据、阶段计划、行动或委托、成果、复盘和计划修订的完整功能。至少一条主线使用真实材料与用户评价走通闭环；其他主线暂时没有真实进展时，可以使用明确标为测试的数据验证功能，真实当前状态及用户核对子项分别记录。用户明确表示当期暂未投入，可以作为该主线真实状态核对的材料，但不能冒充真实成果闭环；系统只是缺数据时仍待用户材料或评价，不能自行推断未投入。不能仅凭入口存在、单主线示例或一份报告判定三主线成长功能完整，也不要求用户为了验收而实际推进暂未投入的主线。三主线状态可以集中由用户核对，已有明确核对证据直接复用，不增加三轮独立审批。

## 8 技术组成与职责

### 8.1 推荐主路径

采用一个常驻DSH Web宿主负责日常交互会话的创建、恢复和写入。项目维护一个范围明确的个人活动插件，连接活动状态、今日入口、来源筛选、摘要更新、归档与调度适配。任务看板复用经验证的现有插件。

DSH官方架构将profile定义为各自的插件与配置组合；当前主分支提供原生timed提问及晚回复恢复机制，但默认提问配置仍需调整。[S2][S3][S4] 这些文档说明不代表目标机器已部署相同能力，发布版本与接口在开发起始验证阶段固定。

**日常交互会话只允许一个活跃宿主写入。** ops和headless可以执行其他短任务，但不同时持有或续写Web正在管理的互动会话。共同DSH_HOME是数据位置配置，不作为跨进程并发安全的证明。

### 8.2 组件责任

| 组件 | 责任 | 必须验证的接口 |
| --- | --- | --- |
| Web宿主 | 电脑／手机入口、独立活动会话、用户回复、原生问题恢复 | 会话创建与恢复、消息提交、活动定位、preset实际配置 |
| 个人活动插件 | 业务日期与进度、来源引用、日程策略、去重、摘要状态、今日页面 | DSH持久事件订阅、插件服务调用、可恢复会话关联 |
| 日常调度适配 | A1–A3唯一到点触发来源，变更日程、暂停、漏跑核对 | 持久计划、调度回调、时区、重启补偿 |
| 看板及其调度 | 明确委托的任务排期、执行与用户验收 | 建卡、独立执行、成果引用、返修及验收限制 |
| 记录与摘要处理 | 完整导出、增量索引、A2/A3摘要、修订传播 | 原始事件读取、按来源筛选、原子写入和版本核对 |
| 可选短任务环境 | 必要的检索、准备或摘要计算 | 独立工作目录、有限工具、结果回传与凭据 |

默认A1–A3的业务调度由个人活动插件统一管理，优先复用选定版本的宿主作业／计时能力。若采用dsh-routines，其角色限定为触发适配器，必须替换该调度入口，不能再登记第二份cron。看板调度只处理明确委托，不能重复注册A1–A3。

dsh-routines作者文档描述的是one-shot运行与摘要交付，并给出常驻命令dsh --profile ops；本文不假定它已提供无模型的业务事件回调。[S5] 若其接口不能直接满足确定性触发，则实现有限的宿主调度模块；不通过让一个模型“记得调用建活动工具”来替代唯一性和恢复规则。

上述职责是项目设计；具体DSH方法名、插件入口和安装命令以固定版本的公开接口为准，不把本文的逻辑操作名冒充现成API。

### 8.3 持久实体

个人活动数据建议使用SQLite；DSH会话和看板仍保留各自权威存储。

| 实体 | 最少字段 |
| --- | --- |
| 活动 | activity_id、用户、routine_id、业务日期、时区、状态、当前步骤、session_id、版本 |
| 持久入站记录 | 稳定提交ID、目标活动、入站时间、持久回执、向DSH交接状态及原生消息引用 |
| 回复引用 | activity_id、问题定位、原生消息ID、接收时间、回答类别、处理状态 |
| 摘要 | activity_id、内容、输入版本或事件游标、人工更正版本、生成时间、有效状态 |
| 日程与偏好 | 明确日程、用户变更指令来源、暂停范围、下一次时刻、通知与免打扰设置 |
| 待执行效果 | 效果ID、幂等键、类型、状态、尝试次数、回执和错误 |
| 画像与成长引用 | 条目ID、来源、作用域、有效期、确认状态、目标和证据引用 |
| 修订与删除 | 目标ID、修订关系、原因、时间、影响范围、恢复时过滤标记 |

原生问题状态与业务活动进度分工明确：DSH保存问题及回复事件；业务层保存“反思到了哪一维”等流程状态。模型可以帮助理解回复，但合法步骤转换、唯一性、权限和最终验收由程序约束。

### 8.4 一次活动的执行链路

1. 调度产生例程与业务日期，业务事务创建或返回已有活动。
2. 先保存会话创建意图，再由Web宿主创建或找回对应独立会话。
3. 生成内容或当前问题，使用经验证的原生timed模式保存待答问题。
4. 前台等待结束后，当前计算可结束；活动继续待回复，不发模型轮询。
5. 用户回复先取得服务端持久入站回执，再进入模型处理；业务层按稳定提交ID及原生消息引用去重，更新进度及摘要需求。
6. 仅在当前问题得到回答、明确跳过或用户改变流程后继续下一步。
7. 摘要以输入版本生成并核对提交；通知、导出分别保留各自回执。
8. 重启后核对活动、会话、待执行效果和已保存消息，续接未完成步骤。

必须覆盖“会话已创建、session_id尚未写回时崩溃”的情况。优先将activity_id写入受支持的可查询元信息；若固定版本无法可靠查询，进入待核对状态，不盲目创建第二份。类似原则适用于建卡、通知和摘要提交。

**“已保存”必须以持久回执为依据。** 优先验证并复用DSH原生durable inbox。官方架构中，请求准备和正式用户消息提交存在先后关系，不能仅凭浏览器提交成功推定故障前已落盘。[S4] 固定版本若不能保证模型不可用时先保存输入，项目以事务性入站队列补齐；向DSH交接使用稳定关联键，核对原生事件后再完成交接，不维护两套可独立修改的正文。

网络重试沿用同一提交ID。交接结果无法核实时保留待核对，不盲目重复投递。尚未收到服务端持久回执时显示“未确认保存”并保留本地草稿；已获回执但模型不可用时显示“回答已保存，处理稍后继续”。归档覆盖已持久入站但尚待交接的内容，并在交接后按同一提交ID合并展示。

### 8.5 原生能力和第三方插件选择

| 项目 | 文档依据与选型要求 |
| --- | --- |

## 9 Linux部署与长期运行

### 9.1 部署参数与运行身份

部署阶段先记录目标发行版、CPU架构、Node与DSH版本、已存在服务、端口、数据目录、实际手机系统与通知通道。不得把聊天环境当作目标Linux主机。

由systemd或目标发行版等效机制管理Web宿主、所需调度及维护进程。后台在开机后、无桌面登录或SSH会话时可运行。使用明确服务账户、绝对工作目录、受控数据目录和显式环境，不依赖交互shell初始化脚本。

实际部署记录包含版本或提交、插件锁定清单、数据位置、可重复启动方式及恢复步骤。Node最低版本依所锁版本的声明核实，不以旧安装笔记作为唯一依据。

官方发布说明记录过Web和headless默认凭据来源的差异，因此每种实际运行环境都必须独立验证模型调用；日志和验收截图不得包含密钥。[S7]

### 9.2 远程接入与通知

首选使用受认证的私有访问路径进入Web。Tailscale Serve可作为候选，设置可信访问来源时同时验证实际授权边界。官方说明Serve后台配置可跨重启恢复；Android的Always-on有助于自动启动，但手机多VPN限制需要实际考虑。[S8][S9][S10]

验收至少覆盖锁屏后重开、Wi-Fi与移动网络切换、短时断网、错误凭据、从通知进入指定活动。手机断联不停止服务器调度。

QQ或其他辅助渠道只发送轻量通知；保底派活必须能关联同一用户与明确任务，消息重复不得重复建卡。通道不可用时页面仍可用，并显示通知能力状态。锁屏通知未实测时保留PENDING_REAL_DEVICE，不宣称完成。

### 9.3 故障与预算

界面显示今日运行状态、最近成功时间、失败原因、待用户动作、摘要积压、最近备份、存储占用、当前版本及调用统计。诊断详情折叠，普通用户能直接理解下一步。

建议工程默认：后台实际生成并发2，单步实际执行超时5分钟，自动重试最多2次，总计最多3次尝试。不同任务可以覆盖执行上限；用户思考时间不计入实际计算超时。

后台自动任务默认每日60000、每月1000000个模型输入与输出token额度，任一额度先耗尽即停止新的自动生成；首次设置可调整。单次后台请求默认最多8192个生成token，可按任务下调，不沿用供应商可能过大的默认值。推理token按所选模型的实际统计口径纳入；若与可见输出分开限额，分别约束并汇总预留。这些是应用消耗控制参数，不代表已估算的货币金额。主会话中的用户主动请求和明确委托另行显示用量及其任务预算，不静默借用后台额度。

所有后台请求，包括自动续轮、工具返回后的后续调用、摘要及各层重试，经过统一的预算准入和记账。调用前按请求输入及最大允许输出预留额度，结束后按实际可得用量结算；预留、结算和释放通过持久事务更新，两个并发请求不得重复占用同一份额度。用量未知或进程中断时保留未核实预留，不按零处理、不因重启清零；之后按回执核对。

额度不足时暂停新自动生成，保留原文记录、查看和手动恢复入口，不把待处理活动标为完成。提高额度或进入新预算周期后按既定恢复规则继续，不批量补跑过去日期。无法约束或核对模型用量时，该供应商的严格预算子项不得标为通过。支持另设货币预算；价格依据、币种和更新时间必须明确，不能伪造实时费用。不得自动切换到更贵模型。

模型不可用时按8.4先取得持久入站回执，再显示保存状态；反复故障使用有界退避，避免不停调用或反复通知。

预算不足不改变每日计划：仍创建或复用当天活动，提供可读状态和按规则的一次首次呈现；可用的基础问题以不调用模型的方式呈现，学习内容等等待额度恢复，不伪造已生成。预算以业务时区的自然日和自然月计数；时区变更不清除已发生的消耗。统计同时显示已结算、已预留和待核对用量，便于判断暂停原因。

### 9.4 备份与恢复

建议默认每日03:30执行不依赖模型的加密一致性备份，保留7个每日、4个每周及6个每月恢复点；长期原始档案按独立保留规则保存，不能把恢复点数量误当成原文保留期限。

备份包含：DSH会话与附件、尚待交接的入站记录、个人业务数据库、摘要及人工更正、画像、任务账本与附件、成长计划、相关preset与skill、业务设置、插件清单及数据格式版本。采用数据库支持的一致性备份，并在受协调的检查点或短时暂停写入后汇总相关文件，不直接随意复制正在写入的数据库。看板JSON导出不包含图片附件，需单独覆盖其assets。[S6]

原始资料可以本地可读，异机备份必须加密；私有git不能替代加密。密钥或恢复口令由用户妥善保管，不能只存在于唯一备份内。

修订／删除账本和已发生外部动作的记录应持续独立保存，并加密复制到可恢复位置，不能只存在于较旧的周期快照。记录其最新保护时间；回执是否可查、复制延迟以及可能丢失的时间段均纳入恢复报告，不承诺未知时间段绝无重复或遗漏。

恢复先进入隔离核对模式，暂停全部自动执行，包括日常及看板调度、Agent自动续跑、待执行效果派发和通知；相关历史内容不自动进入模型或重新建立画像。用独立保存的最新可得修订／删除账本、外部动作记录和通道回执核对旧快照。记录缺失时标记“恢复后状态未知”，禁止直接重放，受影响内容保持隔离；不能把未知状态写成已通过。核对后的动作才按当前规则恢复，不重放所有过去任务或已发通知。

核心恢复验收至少在另一目录或备用环境实际恢复一次，检查未答活动可继续、任务与附件关联完整，并记录耗时。完整迁移还须在不依赖原实例运行状态的干净目录或新实例中，依据版本清单准备环境，导入完整导出、重建索引并核对原文、画像、活动、任务、成长关系及附件；必要凭据重新配置，不能依赖原机器的隐式环境或绝对路径。

跨机器故障恢复需要已验证的异机目标；若尚未提供，只能声称同机恢复演练通过，异机保护和相关核对账本的异机可用性保持待配置。恢复保证仅覆盖明确恢复点及可取得核对记录的时间范围。

### 9.5 容量和升级

容量目标是增长可见、可预估、可归档。区分长期原文与附件、可再生索引导出、短期日志。只清理已经可恢复的缓存和按规则到期的诊断数据；待答活动、唯一原文和有效成果不得由会话清理插件误删。

DSH官方目前仍说明存在兼容性破坏变更。[S1] 生产使用固定版本；升级先在隔离副本验证数据迁移、晚答恢复与看板执行，再保存可回退版本。回滚包括应用与数据兼容关系，不能只恢复旧程序而忽略已经变更的数据库。

### 9.6 本地保存与模型调用

原始档案和结构化记录默认保存在自己的Linux主机；生成内容和摘要时，模型服务会接收当前请求所需的相关内容。按作用域选择背景，不把完整历史每次全部发送。设置页应清楚显示所选模型服务及实际使用的背景范围。

核心可用通过要求全部核心必需场景及其必要子项为PASS；完整交付通过要求全部已约定的必需场景及必要子项为PASS。FAIL、BLOCKED及各类PENDING均阻止对应交付门通过。允许发布可体验版本并报告已完成部分，但不能命名为完整交付。只有明确列为可选的增强项可以在完整交付后继续保留；范围调整由用户明确决定。

三主线成长、三渠道导入及完整迁移属于已约定范围。若确需削减，须通过明确范围变更处理，不能在实施过程中自行消失。
